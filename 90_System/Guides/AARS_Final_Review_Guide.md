# AARS_Final_Review_Guide

## 1. Purpose

This guide explains how to conduct a final review for a bounded AARS system-building round.

It is intended to:
- define what “final review” means in AARS
- distinguish final review from ordinary weekly or project review
- provide a bounded closure-oriented review routine
- support explicit judgment about whether the current round should continue, freeze, or transition

This is a final review guide, not a model.

---

## 2. Core Principle

The core principle is:

**final review should judge round-level completeness, not just file-level existence**

This means final review asks:
- did this round actually achieve its bounded purpose?
- is the resulting baseline coherent?
- what remains unfinished but tolerable?
- what should happen next?

Final review is not just checking whether many files were created.

---

## 3. When to Run a Final Review

Run a final review when:
- a bounded system-building round is nearing closure
- a pilot loop is nearing freeze
- a production-readiness phase is nearing decision
- a large structuring pass is ending
- a baseline note is about to be issued

Do not run final review every day.  
It is a bounded closure-level event.

---

## 4. Review Scope

A final review should cover:

- what this round intended to do
- what was actually completed
- what became strong enough
- what remains weak
- what baseline now exists
- what should happen next

It should remain bounded to one round, not everything in the entire system history.

---

## 5. Final Review Inputs

A final review should normally inspect:

### Core System Inputs
- system home
- current baseline release note
- production readiness checklist
- production readiness review note if available

### Governance Inputs
- review notes
- latest stable view
- freeze notes
- closure checklist

### Structural Inputs
- file placement guide
- directory architecture guide
- active projects home
- project status register

### Validation Inputs
- pilot outputs
- frozen baselines
- runtime prototype evidence if present

---

## 6. Final Review Questions

A final review should answer at least:

1. What bounded round are we reviewing?
2. What was the intended outcome of this round?
3. What was actually completed?
4. What is now strong enough to preserve?
5. What remains incomplete but acceptable?
6. What remains blocking?
7. What is the current latest stable system anchor?
8. What is the correct next move after this round?

These questions define the review.

---

## 7. Core Final Review Checklist

### A. Round Identity
- [ ] Is the current review scope bounded?
- [ ] Is the round objective explicit?
- [ ] Is this review actually for one closure-worthy round?

### B. Completion Check
- [ ] Were the intended major outputs created?
- [ ] Were the outputs placed correctly?
- [ ] Were key system gaps actually reduced?

### C. Coherence Check
- [ ] Are the resulting artifacts coherent together?
- [ ] Do the models, guides, and templates align?
- [ ] Is overlap tolerable or still too confusing?

### D. Continuity Check
- [ ] Is the latest stable view clear?
- [ ] Is the current baseline understandable?
- [ ] Would a future session know how to continue from here?

### E. Decision Check
- [ ] Continue current round
- [ ] Freeze this round’s baseline
- [ ] Start next maturity phase
- [ ] Recover or revise weak areas first
- [ ] Archive / preserve historical state where needed

---

## 8. Strong Completion Signals

A round is likely close to completion when:
- the main intended files exist
- the files are aligned in role
- the system home reflects the current structure
- active/frozen/archive distinctions are visible
- stable view and next-step logic are clear
- major contradictions have narrowed materially

These are stronger signals than file count alone.

---

## 9. Weak Completion Signals

A round is likely not ready for final review closure if:
- files exist but are weakly placed
- system navigation is stale
- stable view is unclear
- production readiness is still mostly assumed
- pilot evidence is missing
- templates exist but are not yet usable
- guides overlap without clear role distinction

These indicate more strengthening is needed.

---

## 10. Final Review Output States

A final review should end with one of the following:

- **Round Closure Allowed**
- **Freeze Recommended**
- **Continue With Focused Refinement**
- **Recover / Consolidate Before Closure**
- **Production Readiness Candidate Confirmed**
- **Production Ready With Caution**
- **Not Yet Ready for Production Review**

These make the closure explicit.
