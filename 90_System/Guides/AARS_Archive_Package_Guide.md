# AARS_Archive_Package_Guide

## 1. Purpose

This guide defines what should be included in an archive package when AARS archives a project state, baseline, or historical artifact group.

It is intended to:
- prevent archive from becoming a dumping ground
- ensure archived materials remain interpretable
- preserve historical traceability
- distinguish archive packages from freeze packages

This is an archive package guide, not an archive model.

---

## 2. Core Principle

The core principle is:

**archive the historical state together with its interpretation context**

This means archived material should include enough surrounding context to answer:
- what this was
- why it is no longer active
- what replaced it, if anything
- why it still matters historically

Archive without context weakens system memory.

---

## 3. Why Archive Packages Matter

Without an archive package:
- old baselines become hard to interpret
- historical review decisions are lost
- superseded structures remain confusing
- users cannot distinguish current from historical logic
- future recovery or comparison becomes harder

Archive packages preserve historical meaning, not just old files.

---

## 4. Minimum Archive Package

A minimal archive package should normally include:

1. archived artifact or baseline  
2. archive note  
3. relation to superseding or active state  
4. historical-value note  
5. navigation update or archive index update  

This is the minimum interpretable archive set.

---

## 5. Recommended Archive Package by Scope

## A. Project Archive Package
Should usually include:
- archived project baseline or key state
- archive note
- final project status note
- relation to active or frozen replacement state if any

## B. Pilot Archive Package
Should usually include:
- frozen or superseded pilot asset
- archive note
- final pilot judgment
- link to stronger replacement or historical conclusion

## C. System Archive Package
Should usually include:
- archived system baseline or superseded model
- archive note
- relation to current system baseline
- note on why historical retention still matters

---

## 6. Archive Note Content

Every archive package should at least clarify:

- what is being archived
- why it is being archived
- whether it is superseded or simply inactive
- what remains active instead
- why the archived material still has value

If these are missing, the package is weak.

---

## 7. Archive Package vs Freeze Package

### Freeze Package
Preserves a state as a reusable reference baseline.

### Archive Package
Preserves a state as a historical or inactive reference package.

### Difference
Freeze supports active inheritance.  
Archive supports historical traceability.

Do not collapse the two.

---

## 8. Archive Package Triggers

An archive package is usually appropriate when:

- a stronger baseline has replaced the current one
- a project is no longer active
- a frozen baseline has aged out of active reference use
- an old system note should remain historically visible but not active
- a project branch is closed and should not clutter active space

Archive should follow explicit trigger logic.

---

## 9. Archive Package Red Flags

Archive packaging is weak if:

- only the old file is moved
- no reason for archive is recorded
- no relation to the newer active state is given
- archive is being used to hide unresolved active problems
- active and archived states remain indistinguishable

These are the main archive-package failure modes.

---

## 10. Human / GPT / Codex Roles in Archive Packaging

### Human
- approves major archive moves
- decides whether historical value is strong enough to preserve
- judges whether material is truly no longer active

### GPT
- recommends archive package contents
- explains historical relationship and archive rationale
- helps distinguish archive from freeze

### Codex
- moves or copies files when approved
- generates archive notes
- updates indexes and MOCs
- should not archive major assets silently
