# AARS_Project_Operating_Guide

## 1. Purpose

This guide explains how to operate an AARS project from initiation to freeze.

It is intended to:
- provide a practical project operating sequence
- reduce ambiguity in project setup and progression
- connect system models to daily project behavior
- define what a project should produce at each stage
- support bounded, reviewable, and reusable project execution

This guide is an operating manual, not a system-definition document.

---

## 2. Core Principle

The core project-operating principle is:

**start bounded, execute visibly, review explicitly, freeze deliberately**

This means:
- do not begin with broad generation
- do not execute without project framing
- do not skip objectization where needed
- do not continue without reviewable state
- do not freeze without explicit judgment

---

## 3. Standard AARS Project Lifecycle

An AARS project should usually pass through the following stages:

1. Project Initiation  
2. Project Framing  
3. Structuring  
4. Capability Preparation  
5. Bounded Case Execution  
6. Review and Stabilization  
7. Freeze / Extend / Recover Decision  
8. Knowledge Capture  

These stages may loop, but they should remain visible.

---

## 4. Stage 1 — Project Initiation

## Goal
Create the minimal project container.

## Required Actions
- define project identity
- define domain/topic
- define why this work exists
- create project directory
- create project home placeholder
- create charter placeholder

## Minimum Outputs
- project folder
- project home file
- project charter file

## Key Rule
Do not begin serious execution before the project has an identity and container.

---

## 5. Stage 2 — Project Framing

## Goal
Bound the project before it expands.

## Required Actions
- define intent
- define goal
- define scope
- define non-goals
- define success criteria
- define initial stage flow

## Minimum Outputs
- project charter
- initial project home links
- working questions list

## Key Rule
A project without bounded framing is not yet ready for capability or case execution.

---

## 6. Stage 3 — Structuring

## Goal
Stabilize the project’s conceptual and knowledge structure.

## Required Actions
- identify core concepts
- stabilize terminology
- create glossary if needed
- create taxonomy if needed
- create concept map if needed
- validate layer distinctions if the project is concept-heavy

## Minimum Outputs
Depending on project type:
- glossary baseline
- taxonomy baseline
- concept map
- layer validation note

## Key Rule
Do not jump to total framework synthesis before structure is good enough.

---

## 7. Stage 4 — Capability Preparation

## Goal
Identify and formalize the first reusable operations.

## Required Actions
- identify candidate capabilities
- create capability catalog
- select first-wave bounded capability family
- formalize the first capability objects
- define which capability will be used in the first case

## Minimum Outputs
- capability catalog
- at least one formalized capability object
- capability-use plan for first case

## Key Rule
Prefer a small bounded capability family to premature capability inflation.

---

## 8. Stage 5 — Bounded Case Execution

## Goal
Run at least one bounded case that produces a governed object chain.

## Required Actions
- choose the case
- define in-scope / out-of-scope
- invoke one or more capabilities
- produce dependency / risk / health outputs
- record stable view and recovery/no-recovery logic

## Minimum Outputs
- invocation record
- dependency object
- risk object
- health snapshot
- stable view note
- recovery path or no-recovery-needed conclusion

## Key Rule
Without a bounded case, the project remains structurally descriptive rather than operational.

---

## 9. Stage 6 — Review and Stabilization

## Goal
Assess whether the project is now reviewable, conditionally stable, or stable.

## Required Actions
- review scope discipline
- review object-chain completeness
- review capability usefulness
- review structural coherence
- identify unresolved but tolerable issues
- identify major instability if present

## Minimum Outputs
- review note
- updated health judgment
- updated stable view
- recommended next step

## Key Rule
Review must end in an explicit decision state, not vague commentary.

---

## 10. Stage 7 — Freeze / Extend / Recover Decision

## Goal
Decide what should happen after the first loop is complete.

## Decision Options

### Option A — Freeze
Use when the current baseline is stable enough to preserve.

### Option B — Extend
Use when the project remains bounded and useful expansion is justified.

### Option C — Recover
Use when major instability prevents safe continuation.

### Option D — Close Current Loop
Use when the current pilot loop is complete and the project should pause or transition.

## Minimum Outputs
- freeze note or frozen baseline
- extension plan
- or recovery path

## Key Rule
Do not allow the project to drift into the next phase without an explicit decision.

---

## 11. Stage 8 — Knowledge Capture

## Goal
Place validated project outputs into the correct long-term locations.

## Required Actions
- decide which files remain project-local
- decide which files become reusable knowledge
- decide which files become output assets
- decide which files become continuity assets
- decide which files should be archived

## Minimum Outputs
- updated file placement
- updated MOCs / indexes
- frozen baseline or continuity anchors preserved

## Key Rule
Knowledge capture should follow review and stable-view logic, not happen blindly.

---

## 12. Minimum Project File Set

A minimally well-formed AARS project should normally include:

### Project Core
- project charter
- project home
- working questions

### Structuring Files
- glossary baseline (if needed)
- taxonomy baseline (if needed)
- concept map (if needed)

### Capability / Case Files
- capability catalog
- at least one capability object
- at least one bounded case file

### Review / Continuity Files
- review note
- health / stable view related files
- freeze or recovery file where appropriate

---

## 13. Project Entry Checklist

Before beginning real work, confirm:

- project identity exists
- project folder exists
- charter exists
- project home exists
- goal is explicit
- scope is explicit
- non-goals are explicit
- initial next step is clear

If not, the project is not yet properly initiated.

---

## 14. Project Mid-Execution Checklist

During active work, confirm:

- current step is known
- current objective is known
- current capability is known
- bounded case boundary is still valid
- dependency/risk/health visibility exists if required
- latest stable view is known
- next-step recommendation is explicit

If not, execution quality is weakening.

---

## 15. Project Freeze Checklist

Before freezing, confirm:

- the current loop is complete
- project review is complete
- stable view is clear
- the baseline is reusable
- unresolved items are documented
- freeze is preferred over ongoing churn

If not, the project should likely remain active or reviewable.

---

## 16. Common Project Failure Modes

This guide protects against:

### Failure 1 — Start Without Framing
The project begins with content generation before charter and scope exist.

### Failure 2 — Endless Structuring
The project keeps refining terminology and taxonomy without moving to capability or case execution.

### Failure 3 — Capability Inflation
Too many capabilities are defined before any bounded case is run.

### Failure 4 — Descriptive Case Only
The case is described, but not objectized.

### Failure 5 — Review Without Decision
A review exists, but no continue/freeze/recover judgment is made.

### Failure 6 — Capture Without Classification
Files are moved into the vault with no controlled placement logic.

## 17. Recommended Human / GPT / Codex Split

### Human
- define project intent
- approve scope
- choose freeze / extend / recover
- validate strategic decisions

### GPT
- assist with framing
- assist with structuring
- review progression
- recommend next step
- check governance discipline

### Codex
- scaffold project files
- normalize frontmatter
- update MOCs / indexes
- generate structured object files
- run bounded repository automations
