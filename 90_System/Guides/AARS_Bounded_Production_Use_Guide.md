# AARS_Bounded_Production_Use_Guide

## 1. Purpose

This guide explains how AARS should be used in bounded production mode after it reaches sufficient readiness.

It is intended to:
- define what “bounded production use” means
- prevent uncontrolled expansion after production transition
- explain how to operate AARS safely in real use
- preserve governance, continuity, and portfolio clarity under production conditions

This is a production-use guide, not a readiness checklist.

---

## 2. Core Principle

The core principle is:

**production use should remain bounded, not unlimited**

Even if AARS becomes production ready, it should still operate through:
- bounded projects
- bounded cases
- explicit review
- stable-view-based continuation
- explicit freeze / archive decisions

Production ready does not mean unbounded or uncontrolled.

---

## 3. What Bounded Production Use Means

Bounded production use means:

- the system is used for real active work
- the work is still organized as bounded projects
- project states remain visible
- object-chain expectations remain explicit
- stable view and next-step logic remain active
- automation remains constrained by governance

This is different from full-scale open expansion.

---

## 4. Entry Conditions for Bounded Production Use

AARS should only enter bounded production use when:

- the production readiness checklist is substantially satisfied
- at least one meaningful pilot has proven the loop
- system navigation is coherent enough
- project templates are usable
- review and stable view discipline are operating in practice
- frozen and archived states are distinguishable

If these are not true, AARS should remain in simulation or candidate mode.

---

## 5. Production Use Scope Rule

Production use should begin with:

- one or a few active projects
- controlled project portfolio growth
- limited automation scope
- explicit status tracking

It should **not** begin with:
- many simultaneous uncontrolled pilots
- broad domain sprawl
- implicit project starts without charters
- invisible baseline changes

Bounded production use must start small.

---

## 6. Core Production Routine

In bounded production use, the standard routine is:

1. create or activate bounded project  
2. confirm project status and latest stable view  
3. run bounded work loop  
4. review explicitly  
5. update stable view if justified  
6. decide continue / freeze / recover / archive  
7. update portfolio state  

This is the production operating rhythm.

---

## 7. Production Project Start Rule

Every new production project should:

- use the project template or pilot template
- define goal and track explicitly
- define scope and non-goals
- be registered in the active project register
- begin with bounded expectations

There should be no “silent project creation” in production use.

---

## 8. Production Review Rule

In bounded production use:
- every meaningful loop should still end with review
- review should still produce explicit judgment
- stable view should still be checked
- next-step logic should still be bounded

Production use must not weaken governance discipline.

---

## 9. Production Stable View Rule

In bounded production use:
- every active project should have a current latest stable view
- the stable view should be visible enough
- continuation should not proceed from unstable new work by default
- Codex automations should respect stable-view-sensitive files

This is one of the most important production controls.

---

## 10. Production Freeze Rule

In bounded production use:
- freeze should still remain explicit
- frozen baselines should be clearly preserved
- frozen baselines should not be casually reopened
- new work should inherit from frozen baselines deliberately, not accidentally

Production use should strengthen freeze discipline, not weaken it.

---

## 11. Production Archive Rule

In bounded production use:
- archive should be used to separate inactive historical material from active baseline material
- archive decisions should remain explicit
- archive packages should preserve historical meaning
- archive should not be used to hide unresolved active confusion

Archive remains part of safe production operation.

---

## 12. Portfolio Rule in Production

In bounded production use:
- all active projects should be visible at system level
- active / frozen / paused / recovering / archived states should be distinguishable
- priorities should be explicit
- cross-project conflicts should be surfaced early

The active project portfolio should remain governable.

---

## 13. Automation Rule in Production

Automation in production should:
- stay bounded
- operate within explicit file/project scope
- produce visible outputs or reports
- avoid silent changes to stable-view-sensitive assets
- avoid freeze / archive / promotion decisions without review

Production automation must remain safer than simulation automation.

---

## 14. Recommended Production Limits (Early Phase)

During early bounded production use, it is wise to limit:

- number of simultaneously active projects
- number of new domain families introduced at once
- number of automation types running without review
- number of major structural reorganizations per cycle

These limits help preserve system coherence.

---

## 15. Production Red Flags

AARS bounded production use is weakening if:

- projects start without registration
- stable view is no longer maintained
- review becomes optional
- active/frozen/archive states blur together
- automation begins making hidden state changes
- portfolio priority is no longer explicit

These are production-governance warning signs.

---

## 16. Human / GPT / Codex Roles in Production Use

### Human
- approves project starts
- approves major freeze / archive / promotion decisions
- manages portfolio priorities
- decides when recovery is necessary

### GPT
- supports framing, review, next-step logic, and governance reasoning
- helps keep boundedness visible
- helps detect drift and baseline weakness

### Codex
- handles bounded structural work
- generates files and updates indexes
- runs safe automation
- supports runtime and prototype refinement

Production use is still multi-role and governance-aware.

---

## 17. Production Success Condition

Bounded production use is working when:

- new projects can start cleanly
- active projects remain visible
- bounded loops reach review and stable-view updates
- frozen baselines are preserved clearly
- automation remains helpful but bounded
- the system stays interpretable over time

That is the minimum sign of healthy production use.

---

## 18. Final Statement

AARS bounded production use means real work can now proceed through the system’s governed project, review, stable-view, and baseline logic without losing boundedness, clarity, or continuity.
