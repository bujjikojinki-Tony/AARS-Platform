# AARS_Onboarding_Guide

## 1. Purpose

This guide explains how a new user should begin using AARS.

It is intended to:
- reduce onboarding friction
- explain the minimum system entry path
- clarify what to read first
- show how to start a first project or pilot
- prevent new users from getting lost in the growing document system

This is an onboarding guide, not a system model.

---

## 2. Core Onboarding Principle

The core principle is:

**do not start by reading everything**

A new user should not try to absorb all AARS files at once.

Instead, onboarding should proceed through a bounded entry sequence:
1. understand what AARS is
2. understand how AARS is used
3. understand how one project begins
4. run one bounded pilot or simulation
5. only then expand into deeper system layers

---

## 3. What AARS Is in One Sentence

AARS is a governed AI-native research operating system that moves work from loose discussion into bounded projects, reusable capabilities, governed object chains, stable continuation states, and reusable knowledge assets.

This is the single-sentence orientation statement for onboarding.

## 5. What a New User Should Not Read First

A new user should **not** begin by reading all of these first:
- every system model
- every guide
- every checklist
- every pilot artifact
- every archive note

This creates onboarding overload and weak operational understanding.

The user should first learn the operating pattern, then deepen selectively.

---

## 6. Minimum Entry Understanding

A new user should understand the following minimum concepts:

- project
- goal
- track
- stage
- capability
- bounded case
- object chain
- latest stable view
- review
- freeze

If these concepts are still unclear, the user should not yet try to build advanced multi-project workflows.

---

## 7. First Project Rule

A new user should not start with a huge domain project.

The first project should be:

- bounded
- small
- operationally simple
- likely to reach a reviewable state quickly

Good first choices include:
- a micro structuring project
- a small migration project
- a capability formalization mini-project
- a bounded simulation pilot

AARS is best learned through one controlled loop.

---

## 8. First Pilot Rule

If using a pilot, the first pilot should aim to prove:

- project framing works
- one bounded case can be defined
- one capability can be exercised
- one object chain can be created
- one review note can be completed
- one latest stable view can be recorded

The first pilot should not attempt domain-total completion.

---

## 9. Toolchain Orientation

A new user should understand the current toolchain roles:

### ChatGPT
Used for:
- framing
- reasoning
- review support
- next-step guidance

### Codex
Used for:
- file generation
- normalization
- structure maintenance
- bounded automation

### Obsidian
Used for:
- persistent notes
- project navigation
- stable knowledge storage
- MOC-based access

### GitHub
Used for:
- version history
- rollback
- frozen-state preservation
- repository integrity

This separation should be clear early.

## 10. First Practical Workflow

A new user should use the following first practical workflow:

1. open `AARS_System_Home`
2. read `AARS_System_Positioning`
3. read `AARS_Usage_Model`
4. create a small project using `AARS_Project_Template`
5. define one bounded goal
6. define one track
7. run one small bounded case or structuring loop
8. create one review note
9. record one latest stable view

If this loop works, onboarding is successful.

## 12. Recommended First Questions for New Users

A new user should ask:

1. What kind of project am I actually trying to run?
2. What is the smallest bounded version of it?
3. What is my primary goal type?
4. What track should dominate first?
5. What should count as success for the first loop?
6. What should definitely not be attempted yet?

These are better onboarding questions than “what can the system do?”

---

## 13. Onboarding Failure Modes

This guide protects against:

### Failure 1 — Read-Everything First
The user reads too much before doing any bounded execution.

### Failure 2 — Start Too Large
The first project is too ambitious and becomes structurally noisy.

### Failure 3 — Tool Confusion
The user expects ChatGPT, Codex, Obsidian, and GitHub to do the same thing.

### Failure 4 — Model Without Practice
The user understands system concepts abstractly but has never run a bounded loop.

### Failure 5 — Project-Free Entry
The user tries to “use AARS” without opening a bounded project.

---

## 14. Recommended First Milestone

A new user should consider onboarding successful when they can do all of the following:

- explain what AARS is in one sentence
- create a bounded project
- identify goal and track
- run one bounded execution loop or structuring loop
- write one review note
- identify the latest stable view
- name the next bounded step

This is the true first milestone.

---

## 15. Human / GPT / Codex Roles During Onboarding

### Human
- chooses the first bounded project
- decides scope limits
- approves the first stable view and next step

### GPT
- explains system logic
- assists framing
- helps classify the first goal and track
- supports first review

### Codex
- scaffolds the first project files
- normalizes structure
- updates links and MOCs
- performs bounded setup tasks

The new user should see these roles early.

---

## 16. Suggested Next Step After Onboarding

After one successful bounded onboarding loop, the next step should usually be one of:

- run a second bounded project
- start a domain pilot
- refine templates and schemas
- begin runtime/interface prototype work

The user should not jump directly from onboarding to broad production claims.

---

## 17. Final Statement

The AARS Onboarding Guide ensures that new users enter the system through bounded understanding and bounded action, rather than through document overload or uncontrolled project ambition.
