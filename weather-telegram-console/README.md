# weather-telegram-console

Telegram control surface for weather market signals.

## Purpose

This repository presents structured signal events to human operators.

It does:
- receive signal payloads
- render Telegram cards
- expose approval / rejection actions
- store operator actions
- support lightweight status / control commands

It does not:
- generate weather forecasts
- score signals
- execute trades directly

## First MVP

The first MVP supports:
- `/start`
- `/status`
- `/signals`
- inline actions:
  - Watch
  - Approve Small
  - Ignore

## Input

This bot consumes `SignalEvent`-style payloads produced by `weather-signal-engine`.

## Output

This bot produces:
- Telegram messages
- operator decisions
- stored approval / rejection actions

## Dashboard Approval Bridge

When the dashboard writes a pending execution intent, it can also write:

- `data/outputs/dashboard_approval_signal.json`
- `../weather-execution-gateway/data/outputs/dashboard_intent_preview.json`

The Telegram console prefers the dashboard approval signal when it exists, so
`/signals` can show the exact dashboard-generated `signal_id` and approval
actions can bind the operator decision to the same `intent_id` consumed by the
execution gateway.

If the signal uses `execution_mode=manual_advisory`, approval means operator
acknowledgement only. It does not authorize autonomous BOT trading. The handler
also appends an `operator_acknowledged_manual_advisory` event to the shared
manual advisory audit log.

The Telegram card also displays probability contract fields such as
`probability_mode` and `execution_constraint`, so heuristic shadow probabilities
are not confused with future calibrated live-approved probabilities.

Useful env overrides:

```bash
export DASHBOARD_APPROVAL_SIGNAL_JSON_PATH=data/outputs/dashboard_approval_signal.json
export DASHBOARD_INTENT_PREVIEW_PATH=../weather-execution-gateway/data/outputs/dashboard_intent_preview.json
export MANUAL_ADVISORY_AUDIT_JSONL=../weather-execution-gateway/data/outputs/manual_advisory_audit.jsonl
```

## Ops Alert Bridge

Telegram console can consume `gate_stack_ops_alerts.jsonl` generated by
comparison-engine runtime checks and enqueue deduplicated notification items:

```bash
weather-telegram-ops-bridge sync-gate-alerts --max-batch 50
```

Outputs:

- `data/outputs/telegram_ops_notifications.jsonl`
- `data/outputs/ops_alert_bridge_state.json`
- `data/outputs/telegram_ops_delivery_log.jsonl`

Queue lifecycle commands:

```bash
weather-telegram-ops-bridge dispatch-ops-queue --max-batch 20
weather-telegram-ops-bridge ack-ops --notification-id <id> --acked-by operator
```

Lifecycle:

- `pending` -> `sent` (dispatch)
- `sent` -> `acked` (ack)

Useful env overrides:

```bash
export GATE_STACK_OPS_ALERTS_JSONL=../weather-comparison-engine/data/outputs/gate_stack_ops_alerts.jsonl
export TELEGRAM_OPS_NOTIFICATIONS_JSONL=data/outputs/telegram_ops_notifications.jsonl
export OPS_ALERT_BRIDGE_STATE_JSON=data/outputs/ops_alert_bridge_state.json
export TELEGRAM_OPS_DELIVERY_LOG_JSONL=data/outputs/telegram_ops_delivery_log.jsonl
```

## Safety posture

No private keys.
No direct execution logic in the bot.
Execution remains downstream and optional.
