

**总体方向已经对齐，主骨架是成立的；但“实时监测预警”“数据标准化”“唯一数据源”“多源采集周期策略”这四块，成熟度并不一致。**  
其中：

- **数据唯一源 / 事实链治理**：已经进入较清晰、较成熟阶段。
- **数据标准化 contract**：主链路 contract 已经较全，但监测采集层的 indicator registry / threshold policy 仍处于 Phase 27 Batch 1 起步状态。
- **实时监测预警功能**：设计上已被正式纳入系统范围，并已有 scaffold，但整体仍是“治理规范已成、最小实现已起、闭环尚未完全收口”。
- **不同数据源的周期策略**：设计原则上已明确要 cache-first、worker 异步、freshness gate，但还没有形成一份完全显式的“按 source 分类的采集周期策略表”。这一块现在最值得补。

下面我分四部分展开。

# **一、按治理规范回看：当前设计文档对齐得怎么样**

## **1. 实时监测预警：已经正式进入架构和需求，但仍处于“规范先行、实现起步”**

最新架构文档已经把系统闭环从原来的三条扩展到**第四条闭环**：

- `observation / forecast / market / resolver / comparison -> alert / anomaly indicators -> dashboard / telegram / automation consumers`。 

功能需求也已经把这件事写成正式业务目标，第 11 条明确要求：

- **单市场预警**
- **family 级异常发现**
- 为 dashboard / telegram / automation 提供统一监测语义。 

测试报告也已经把这些对象纳入验证范围，包括：

- `market_alert_event.v1`
- `market_anomaly_event.v1`
- `indicator_registry`
- 以及监测采集层相关需求 FR-21、FR-22。 

实施状态进一步说明：

- **Phase 27 Monitoring Collection / Indicator Governance** 已进入 `In Progress / Batch 1 Completed`
- 已有：
    - `observation shock`
    - `forecast divergence`
    - `market reaction gap`
    - `family anomaly discovery`
    - `indicator registry`
    - `threshold policy registry`
    - `market_alert_event.v1`
    - `market_anomaly_event.v1`
- 并且注明 scaffold、scripts、event writers 已落地，目标脚本在当前输出上可运行。 

**结论**  
这说明：  
实时监测预警不是“还没进入设计”，而是已经成为**正式系统能力**。  
但从阶段状态看，它还不是“成熟完工”，而是：

**治理规范、contract、目录骨架和最小事件 writer 已经出现，完整的监测闭环还在推进中。**

---

## **2. 数据标准化：主链标准化做得较好，监测采集层标准化刚启动**

详细设计文档对主链数据对象定义已经很完整，核心标准对象包括：

- `MarketSnapshot`
- `MarketRule`
- `ForecastSnapshot`
- `ObservationSnapshot`
- `ProbabilityState`
- `ComparisonPoint`
- `TopParameterView`
- `Data Source Governance Contract`。

并且明确要求：

- 上游事实链拆成五段
- 每一段有唯一输入、唯一输出、可回指引用
- comparison / probability **只做派生，不改写事实上游**
- UI / Telegram / Gateway 只消费同一条事实链，不在展示层重拼事实。

开发报告也已经把这个原则落到了实现检查结果里，例如：

- `market_realtime_simple*.json` 启动时采用**价格优先**，避免 metadata-only 空壳覆盖主快照
- comparison-engine、dashboard、Telegram 各自有 `TopParameterView` 适配器，但 **schema 一致**
- `market_probability` 可由显式字段或 yes/no price 推导
- `TopParameterView` 只做聚合，不改写事实。

但从监测采集层来看，标准化还只是刚起步：  
指标治理规范已经把 registry / threshold policy / indicator event contract 写清楚了，但这部分还是新层，不像主链 schema 那样成熟。

**结论**  
当前数据标准化呈现“两层成熟度”：

- **交易主链标准化：较成熟**
- **监测采集层标准化：已起步，但仍在第一轮收口**

---

## **3. 数据唯一源：这是目前最清晰、最成熟的部分**

这块设计文档已经非常明确，且开发状态与之高度一致。

详细设计和开发报告都反复强调：

- 市场发现、市场录入、resolver、forecast、comparison、展示必须共享同一份可追溯事实源
- `TopParameterView` 不是新的事实源，只是首屏聚合合同
- 同一 `market_id` 的 `market_snapshot` / `market_rule` / `forecast_snapshot` / `comparison_point` 必须能回指到同一条事实链。

甚至已经有专门的数据治理契约：

- `data_source_governance.v1`
- 明确记录：
    - `market_snapshot_ref`
    - `market_rule_ref`
    - `forecast_snapshot_ref`
    - `observation_snapshot_ref`
    - `comparison_point_ref`
- 以及治理规则：
    - single source of truth per market_id
    - derived views must reference upstream refs
    - ui must not rewrite factual fields。

实施状态也已把“唯一真源”推进到更深一层：

- `gate_stack_api.v1` 被定义为跨表面唯一 gate contract
- `probability_contract.v1` 是跨表面概率契约
- `execution_intent.v1` 是 execution gateway 唯一意图对象。

**结论**  
如果只看“单一事实源治理”，当前设计是**对齐且比较成熟**的。  
这块已经不是主要短板。

# **二、就“已实现的实时监测预警功能”来看：现在做到哪里了**

## **1. 已有的部分**

从设计与实施状态看，当前已经具备这些监测采集能力的雏形：

### **单市场预警侧**

- `observation shock`
- `forecast divergence`
- `market reaction gap`
- `market_alert_event.v1` 输出契约
- `run_observation_alert_once.py` 作为最小验证入口。

### **Family 批量异常发现侧**

- `family anomaly discovery`
- `market_anomaly_event.v1`
- `run_family_anomaly_scan_once.py`
- family scanner scaffold。

### **与现有系统的承载位关系**

治理规范已经明确，这一层将作为：

- observation alert 的输入源
- family anomaly scanner 的输出源
- dashboard / telegram / automation 的统一消费依据。 

## **2. 还没有完全做实的部分**

虽然 contract 和 scaffold 已经有了，但从文档判断，以下环节仍未完全成熟：

### **A. 指标到 gate 的联动边界还需更明确**

治理规范已经强调：

- 指标与 gate 分离
- alert / anomaly 不替代 authorization gate、execution gate。 

这点是对的，但在实现层面，当前仍更偏“事件输出”，还不是“完整的运营控制链”。

### **B. family anomaly 中更高级的异常机制还在后续阶段**

治理蓝图里把这些列为后续补齐项：

- `microstructure_stress_detector.py`
- `peer_relative_anomaly.py`
- `intervention_like_scorer.py`。 

这说明 family anomaly 目前更像 **MVP scanner**，不是完全成熟的异常市场发现引擎。

### **C. 监测事件还没有成为唯一上游告警源**

现在系统已有：

- `gate_stack_ops_alert.v1`
- ops bridge
- queue lifecycle
- automation summary。

而治理规范又引入：

- `market_alert_event.v1`
- `market_anomaly_event.v1`。 

这意味着当前系统已经有**两类不同层次的告警语义**：

1. **运行时 gate / ops alert**
2. **市场监测 / anomaly alert**

设计上两者是分开的，这是正确的；但真正的联动策略还需要继续细化，不然容易出现：

- gate 是红灯
- anomaly 是高分
- operator 不知道谁优先

**判断**  
当前实时监测预警功能已进入“可用雏形”，但仍在**第一轮系统化落地阶段**。

# **四、不同数据源采用周期：现在最值得补的一张“采集节奏表”**

这一块是你特别要求我考虑的重点。  
我的判断是：

当前文档已经有“freshness / cache-first / worker 异步 / monitoring”这些原则，但**还缺一份真正明确的 source cadence policy**。

详细设计原则里已经说了：

- 外部请求不阻塞首屏
- 所有外部数据源采用 cache-first 或 worker 异步写入。 

测试和实施状态也一直强调 freshness gate。

但现在最该补的是：**不同 source 不同周期，不应该一刀切。**

我建议这样处理。

## **1. Polymarket 市场数据**

### **A. CLOB / price**

定位：最高频源  
用途：盘口事实、实时反应、price velocity、microstructure stress

建议周期：

- **事件驱动 / WebSocket 优先**
- 聚合写快照：1–5 秒一个 market-level snapshot，或事件触发去抖写入
- freshness threshold：30–90 秒

原因：

- 市场价格与 spread 对 anomaly/ops 最敏感
- 不能用低频轮询替代

### **B. Gamma metadata**

定位：低频补充源  
用途：市场发现、问题文本、结构元数据

建议周期：

- 5–15 分钟
- watchlist / selected market 触发时可临时刷新

原因：

- 元数据不会像盘口那样秒级变化
- 高频拉没有意义

---

## **2. Resolver**

定位：中低频、事件触发优先  
用途：market rule / source contract

建议周期：

- 市场首次进入 watchlist：立即解析
- selected market 变化：立即解析
- 市场 question / metadata 变更：重跑
- 定时回扫：30–60 分钟

原因：

- resolver 是结构解释，不应高频空转
- 但 source contract 改动、registry 更新后要能刷新

---

## **3. Forecast 类数据**

这里要分 source。

### **A. HRRR**

定位：高频短临预测  
适用：美国本土短临、温度/风/降水类市场

建议周期：

- 5–15 分钟拉取“最新已发布有效值”
- 若 source 本身发布时间未更新，则不重复重算
- freshness threshold：1–2 小时

### **B. ECMWF**

定位：较低频全局/区域预测  
适用：日级 forecast、全球范围

建议周期：

- **按发布周期驱动**，不是按短轮询驱动
- 本地检查频率可 15–30 分钟
- 真实快照更新只有在新 run 出现时才写新 snapshot
- freshness threshold：6–24 小时，视 family 而定

### **C. Wunderground / 站点式天气源**

定位：中频站点 forecast / history / local support

建议周期：

- selected market：5–15 分钟
- watchlist：15–30 分钟
- freshness threshold：1–3 小时

**原则**  
forecast 数据不应“盲目短轮询”。  
应该以：

- **source 发布周期**
- **market 紧迫度**
- **family 类型**  
    三者共同决定。

---

## **4. Observation 类数据**

### **A. METAR**

定位：高频近实时 observation  
用途：observation shock、阈值穿越、forecast divergence

建议周期：

- selected market / active alert market：1–5 分钟
- watchlist matched station markets：5–10 分钟
- freshness threshold：30–90 分钟

原因：

- 这是 observation alert 的核心触发源
- 适合做单市场实时预警

### **B. official obs / settlement source**

定位：低频但权威  
用途：结算、label、最终 truth、promotion / validation

建议周期：

- 选中市场：15–60 分钟
- 历史 / label backfill：按小时或按天批量
- freshness threshold：取决于 source，自身 often slower than METAR

原因：

- 不一定足够高频
- 但必须是 truth anchor

---

## **5. 比较层 / 监测层 / 异常层**

这些层不应该按独立 source 周期跑，而应该按**上游事实更新触发**。

### **A. Probability / Comparison**

建议：

- 只要 market / forecast / observation 中任一更新，就增量重算当前 market
- watchlist 批处理可 1–5 分钟

### **B. Observation Alert**

建议：

- observation 更新触发优先
- market 更新次级触发
- selected market 实时、watchlist bounded

### **C. Family Anomaly Scanner**

建议：

- 不要秒级全量扫
- 按 family 做 **5–15 分钟一轮**
- 若某 market 触发高优先级 alert，可做 targeted rescan

原因：

- 全量 family anomaly 扫描成本高
- 多数异常不是秒级必须发现

# **五、我给出的综合判断**

## **1. 当前设计文档的优点**

当前文档在这几个方面已经很强：

- 单一事实链治理清楚。
- 主链 contract 已经成熟。
- 监测采集层已经进入正式架构与实施状态。
- `TopParameterView` 已经把天气参数、forecast 参数、市场参数抬到了首屏。

## **2. 当前最大的不足**

当前最该补的不是再加新页面，而是：

### **A. 明确 source cadence policy**

也就是把：

- CLOB
- Gamma
- resolver
- HRRR
- ECMWF
- METAR
- official obs
- family scanner  
    各自的周期、freshness threshold、触发方式写成正式策略表。

### **B. 明确监测事件与 ops/gate 告警的关系**

现在已有：

- `gate_stack_ops_alert.v1`
- `market_alert_event.v1`
- `market_anomaly_event.v1`

下一步要更明确它们的优先级与流转关系。

### **C. 把监测采集层的 registry / threshold policy 真正做成唯一配置源**

现在规范已经写了，Phase 27 也起步了；下一步关键是别让 detector 自己写死阈值。
