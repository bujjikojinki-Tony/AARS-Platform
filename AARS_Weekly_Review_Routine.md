# AARS_Weekly_Review_Routine

## 1. Purpose

This guide defines a weekly review routine for operating AARS across one or more active projects.

It is intended to:
- provide a repeatable weekly governance rhythm
- prevent long-running drift
- support cross-project visibility
- connect daily execution to bounded portfolio review
- identify what should continue, freeze, pause, recover, or archive

This is a weekly operating guide, not a system model.

---

## 2. Core Weekly Rule

The core rule is:

**daily work advances projects; weekly review governs them**

This means a weekly review should not merely repeat daily work.  
It should ask whether the overall direction, priority, and continuity state are still acceptable.

---

## 3. Weekly Review Scope

A weekly review should normally examine:

- active projects
- latest stable views
- project status changes
- freeze candidates
- recovery candidates
- project priority shifts
- system-level guide or template gaps exposed by recent work

This is wider than a single-project review.

---

## 4. Weekly Review Sequence

A practical weekly AARS review sequence is:

1. Review active project register  
2. Review latest stable view for each active project  
3. Review frozen / paused / recovering states  
4. Review priority order  
5. Review unresolved blockers  
6. Review reusable lessons for the system layer  
7. Decide next weekly focus  

This creates a bounded weekly governance loop.

---

## 5. Step 1 — Review Active Projects

Open:
- `AARS_Active_Projects_Home.md`
- `AARS_Project_Status_Register.md`

Check:
- which projects are active
- whether each status is still accurate
- whether any project has silently drifted into pause / review / recovery condition

Do not assume the register is correct without checking it.

---

## 6. Step 2 — Review Latest Stable Views

For each active project, review:
- current latest stable view
- whether it is still the right anchor
- whether a stronger new anchor emerged this week
- whether the current anchor has weakened

This is one of the most important continuity checks.

---

## 7. Step 3 — Review Frozen / Paused / Recovering States

Check:

### Frozen
- should it remain frozen?
- should any frozen baseline now be archived?
- is anyone accidentally treating it as active?

### Paused
- should it remain paused?
- should it be reactivated?
- should it move toward archive?

### Recovering
- is recovery still active?
- is a new stable anchor now available?
- is the project still too weak to continue?

This keeps non-active states visible.

---

## 8. Step 4 — Review Priority Order

Ask:
- which project should receive next week’s effort?
- which project should deliberately not receive effort?
- has any project become urgent due to continuity or recovery risk?
- is the portfolio over-concentrated on one type of work?

Priority should be explicit weekly, not assumed.

---

## 9. Step 5 — Review Unresolved Blockers

For each active project, check:
- unresolved structural contradictions
- missing object-chain elements
- stale review states
- weak or missing stable anchors
- missing templates or system support

A blocker that persists across multiple weeks should be treated as significant.

---

## 10. Step 6 — Review Reusable Lessons

Weekly review should also ask:

- what patterns repeated this week?
- what should become a guide, checklist, or template?
- what local project behavior now deserves promotion into system knowledge?
- what system model is still too abstract for real use?

This is how AARS improves through use, rather than through isolated theory writing alone.

---

## 11. Step 7 — Decide Next Weekly Focus

At the end of the weekly review, select:

- one primary focus project
- one secondary focus project if needed
- one system refinement target if justified
- one project that should remain untouched

This keeps the next week bounded.

---

## 12. Weekly Review Outputs

A useful weekly review should produce some of the following:

- updated project status register
- updated active-projects home
- updated latest stable view references
- freeze candidate note
- recovery candidate note
- next weekly focus note
- system-improvement shortlist

A weekly review should leave visible governance trace.

---

## 13. Weekly Review Questions

Use these core weekly questions:

1. Which project is currently the real primary project?
2. Which stable anchor is still valid?
3. Which project should freeze?
4. Which project should pause?
5. Which project needs recovery?
6. What system-level gap did this week expose?
7. What should the next week focus on?

These are more important than “how many files changed.”

---

## 14. Good Weekly Review Pattern

A good weekly review should:
- be brief but explicit
- examine all active projects
- verify stable anchors
- decide priorities
- produce one bounded weekly focus decision

It should not become a vague reflection session.

---

## 15. Bad Weekly Review Pattern

A weak weekly review often looks like:
- only checking which files changed
- not reviewing active vs frozen status
- not checking stable anchors
- adding more work without reducing ambiguity
- leaving the next week without a clear bounded focus

This is what the routine is designed to prevent.

---

## 16. Weekly Failure Modes

This guide protects against:

### Failure 1 — Silent Portfolio Drift
Projects change state, but the portfolio layer is never updated.

### Failure 2 — Frozen Project Reopening by Accident
A frozen baseline is treated as active due to lack of review.

### Failure 3 — Multi-Project Overload
Too many projects remain active without explicit priority.

### Failure 4 — No System Learning
Repeated project friction never becomes system refinement.

### Failure 5 — Recovery Blindness
Recovering projects continue to look normal because nobody reviews them weekly.
