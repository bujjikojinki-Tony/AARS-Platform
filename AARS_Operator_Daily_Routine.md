# AARS_Operator_Daily_Routine

## 1. Purpose

This guide defines a practical daily operating routine for working inside AARS.

It is intended to:
- make daily use repeatable
- reduce random context switching
- connect project state, review, and continuity to everyday work
- prevent users from drifting into unbounded execution

This is a daily operating guide, not a system model.

---

## 2. Core Daily Rule

The core rule is:

**start from the current stable anchor, not from whatever feels most urgent**

This means daily work should begin by checking:
- active project
- current stage
- latest stable view
- current bounded next step

AARS daily use is continuity-first, not impulse-first.

---

## 3. Daily Routine Overview

A practical AARS daily routine is:

1. Check active projects  
2. Check latest stable anchor  
3. Choose today’s bounded objective  
4. Execute one bounded loop or one bounded sub-loop  
5. Review what changed  
6. Update stable view if justified  
7. Record next bounded step  

This is the minimal daily rhythm.

---

## 4. Step 1 — Check Active Projects

At the beginning of the day, review:

- `AARS_Active_Projects_Home.md`
- `AARS_Project_Status_Register.md`

Ask:
- which project is active now?
- which project has highest current priority?
- what project should not be touched today?

Do not start by opening random notes.

---

## 5. Step 2 — Check Latest Stable Anchor

For the chosen project, locate:
- latest stable view
- most recent review note
- current stage
- current health state

Ask:
- what is the current safe continuation point?
- has anything since then been accepted as stronger?
- is today’s work continuing, stabilizing, freezing, or recovering?

This prevents daily reset-by-memory.

---

## 6. Step 3 — Choose Today’s Bounded Objective

Define one bounded objective for the session.

Examples:
- draft one capability object
- complete one risk review pass
- update one project home
- run one bounded case sub-loop
- normalize one system directory layer

Do not choose broad objectives such as:
- “improve the whole system”
- “finish everything”
- “rework the vault”

Daily objectives should be small, clear, and reviewable.

---

## 7. Step 4 — Execute One Bounded Loop

Now execute today’s chosen bounded work.

Depending on project state, this may mean:

### Structuring Work
- glossary
- taxonomy
- concept distinctions
- concept map

### Capability Work
- define capability
- revise capability
- scaffold capability objects

### Case Work
- invocation
- dependency
- risk
- health
- stable view candidate

### System Work
- update guides
- normalize models
- improve navigation
- create one missing system artifact

AARS daily use should favor depth in one bounded loop over scattered multi-directional work.

---

## 8. Step 5 — Review What Changed

At the end of the loop, ask:

- what changed?
- what became clearer?
- what remains weak?
- is the result only draft, or reviewable?
- does this change the project’s continuity state?

Use review language, not only content language.

---

## 9. Step 6 — Update Stable View If Justified

Only update the latest stable view if:
- the new state is safer or clearer than the previous anchor
- review supports the change
- continuity would improve from using the new anchor

If not, keep the old stable view and mark the new work as still under review.

This is one of the most important daily disciplines in AARS.

---

## 10. Step 7 — Record the Next Bounded Step

Before ending the day, write down:

- what the next bounded step is
- what not to do next
- whether review, freeze, recovery, or continuation is now appropriate

Do not leave the system without an explicit next-step marker.

---

## 11. Daily Inputs to Check

A good daily session should normally inspect some of these:

- active projects home
- project status register
- project home
- latest stable view
- review note
- current capability or case files
- system home if working at system layer

Not every file is needed every day, but continuity anchors should be checked regularly.

---

## 12. Daily Outputs to Leave Behind

A useful daily session should usually leave behind at least one of the following:

- updated project artifact
- updated object
- updated review note
- updated latest stable view
- updated next-step note
- updated MOC / index
- normalized file structure

AARS daily work should produce traceable state change, not only thought.

---

## 13. Good Daily Session Pattern

A strong daily session usually looks like:

### Start
- identify active project
- identify stable anchor
- define bounded goal

### Middle
- do one bounded piece of work
- keep execution scoped

### End
- review
- decide whether stable view changes
- write next bounded step

This is the recommended standard.

---

## 14. Bad Daily Session Pattern

A weak daily session often looks like:

- opening many notes with no active project
- adding many new files without bounded objective
- changing structure and content at the same time without review
- ending without stable view or next-step update
- mistaking raw activity for governed progression

This is what the daily routine is meant to prevent.

## 15. GPT / Codex / Obsidian / GitHub Daily Roles

### ChatGPT
Use daily for:
- framing the session
- reasoning through ambiguity
- checking next-step logic
- review support

### Codex
Use daily for:
- scaffolding files
- normalization
- bounded repository work
- repetitive structural tasks

### Obsidian
Use daily for:
- reading project home
- reading stable view
- writing notes
- navigating linked knowledge

### GitHub
Use daily for:
- commit history
- rollback safety
- preserving session changes

---

## 16. Daily Failure Modes

This routine protects against:

### Failure 1 — Contextless Work
Work begins without knowing what project is active.

### Failure 2 — Impulse Expansion
The day is driven by whatever seems interesting rather than bounded priority.

### Failure 3 — No Review Closure
A session ends without review or next-step capture.

### Failure 4 — Stable View Neglect
The previous continuity anchor is ignored.

### Failure 5 — Many Small Untracked Changes
Files change, but governance state does not.
