# AARS_Operator_Quickstart

## 1. Purpose

This guide provides the shortest practical entry path for operating AARS.

It is intended to:
- help a user begin using AARS quickly
- reduce startup friction
- provide a minimal operating loop
- connect system understanding to immediate action

This is a quickstart guide, not a full onboarding guide.

---

## 2. Quick Definition

AARS is a governed research operating system that helps you run bounded projects through:
- explicit framing
- reusable capabilities
- bounded cases
- governed object chains
- reviewable continuation
- stable knowledge capture

---

## 3. What You Need Before Starting

Before using AARS, make sure you have:

- a vault/repo structure
- `AARS_System_Home.md`
- `AARS_Project_Template.md`
- `AARS_Project_Operating_Guide.md`
- one place to store project files
- one way to version changes

You do not need a full platform UI to begin.

---

## 4. Read These First

Read these in order:

1. `AARS_System_Home.md`
2. `AARS_System_Positioning.md`
3. `AARS_Usage_Model.md`
4. `AARS_Project_Operating_Guide.md`

After that, start working.  
Do not wait until you understand every file.

---

## 5. Minimal First Loop

Use this first-loop sequence:

1. create one small project  
2. define one primary goal  
3. define one primary track  
4. keep the project tightly scoped  
5. produce one bounded artifact or bounded case  
6. write one review note  
7. identify one latest stable view  
8. decide one next bounded step  

This is the minimum AARS operating loop.

---

## 6. How to Start a New Project

Use `AARS_Project_Template.md` and fill only the essential fields first:

- Project ID
- Project Name
- Project Intent
- Primary Goal
- In Scope
- Out of Scope
- Success Criteria
- Immediate Next Step

That is enough to begin bounded work.

---

## 7. What to Do Next

Once the project exists, choose the dominant path:

### If the work is still vague
Do structuring first:
- glossary
- taxonomy
- concept map

### If the work is already operationally clear
Do capability and bounded case work:
- capability selection
- bounded case
- object chain

### If the work is already mature
Do review, freeze, or packaging

Do not do all paths at once.

---

## 8. Minimum Object Chain

If your project enters operational proof, try to produce at least:

- one invocation
- one dependency object
- one risk object
- one health snapshot
- one latest stable view
- one review note

That is enough to make the project meaningfully operational.

---

## 9. Minimum Review Rule

Every loop should end with a review that answers:

- what is the current condition?
- what is the current stable anchor?
- what is the next admissible step?

If your loop cannot answer those three questions, it is incomplete.

---

## 10. What Not to Do

Avoid these common mistakes:

- starting too large
- skipping project framing
- generating many files without bounded logic
- confusing newest output with safest continuation
- packaging too early
- ignoring review

AARS works best when the first loop is small and clear.

---

## 12. Quick Success Condition

You have used AARS successfully when you can do all of the following in one bounded loop:

- create a project
- choose goal and track
- keep scope bounded
- generate useful structured outputs
- review the loop
- identify the latest stable view
- name the next bounded step

That is enough for a real first success.

---

## 13. Next Step After Quickstart

After one successful loop, choose one:

- run a second bounded project
- begin a domain pilot
- refine templates and schemas
- prototype runtime/interface views

Do not jump straight from quickstart to large-scale production claims.

---

## 14. Final Statement

The fastest way to begin using AARS is not to master every document first, but to run one small bounded loop with explicit framing, explicit review, and an explicit latest stable view.
